## Previous and Current Evidence

- Windows Disk Management exposed the full capacity as unallocated; DiskPart
  reported a peripheral-device write fault during reprovisioning.
- Linux repeatedly reported `Medium Error`, `Peripheral device write fault`,
  and failed `WRITE(10)` commands at both the beginning and end of the device,
  including sectors 0, 1, 2, 3907029134, and 3907029166.
- `Synchronize Cache(10)` failed and the alternate GPT remained invalid while
  the readable primary GPT exposed the 6 MiB `Secure Drive (Locked)` NTFS
  partition.
- `smartctl -x -d sat /dev/sda` and `smartctl -x -d sat,12 /dev/sda` both
  failed because the enclosure rejected ATA pass-through with an unsupported
  SCSI-command field.
- `smartctl -x -d scsi /dev/sda` exposed enclosure-level identity and a
  limited `SMART Health Status: OK`, but reported SMART disabled, no error
  counter log, no self-test log, and unusable 0 C temperature values.
- The block device is not kernel write-protected and advertises enabled read
  and write caches. Primary GPT and locked-partition metadata remain readable;
  actual writes fail with device sense data.

## Failure Classification

**Indeterminate at the enclosure boundary.** The observed write failures are
real and repeat across operating systems, but current evidence cannot isolate
the Seagate Secure controller, USB bridge path, or underlying HDD. The limited
SCSI health summary does not override the error evidence and cannot qualify
the HDD because native ATA identity, attributes, and error telemetry are
unavailable. No evidence supports a firmware-only conclusion.

## Engineering Disposition

**Engineering Reprovisioning Authorized.** The owner has permanently
abandoned recovery of the previous contents. Recovery efforts are complete,
and those contents have no remaining engineering preservation requirement.

This decision supersedes the previous recommendation for enclosure
disassembly and direct SATA qualification before disposition. That future
investigation is intentionally cancelled. The enclosure-boundary failure
classification and all supporting evidence remain historical engineering
facts; owner disposition authority changes the engineering objective without
reclassifying the observed failure.

The successor **AST-000005 Secure Reprovisioning and Engineering
Qualification** mission completed on 2026-07-17. Its verified result is
recorded below without reclassifying the historical enclosure-boundary
failure evidence.

## Engineering Qualification

Qualification on `thaDuke` verified the intact GPT, aligned full-capacity
partition, ext4 filesystem, label, UUID, UUID-based mount, unmount, and
remount. The preserved workload contains one 16 GiB sequential file, nested
metadata directories, 64 original small-file operations, rename evidence,
and delete evidence. The sequential file is exactly 17,179,869,184 bytes and
its completed SHA-256 read returned exit status zero:

`07d217ebccc55480b7afa191674ec5da87f2d14efbc04dbc7e40efe345f16776`

Kernel evidence contains no AST-000005 I/O error, medium error, or write-fault
event during qualification. Enclosure-level SCSI SMART reports `SMART Health
Status: OK`, but SMART is reported disabled, temperature is an unusable 0 C,
error counters and self-test logs are unavailable, and both `sat` and
`sat,12` pass-through fail with an unsupported SCSI-command field.

The qualification artifacts are preserved under `engineering-qualification`
as engineering evidence. Their future removal requires separate authority.

## Mount Strategy

No persistent mount is configured. Because the asset is available but has no
assigned operational role, automatic boot-time mounting would create an
unsupported infrastructure dependency. Mount by filesystem UUID manually for
authorized work; define a persistent mount only with a future role assignment.
