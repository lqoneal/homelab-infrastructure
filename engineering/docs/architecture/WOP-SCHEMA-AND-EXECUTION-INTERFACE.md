# Canonical WOP Schema and Execution Interface

## Canonical contract ownership and convergence

This document is the canonical owner of the shared semantic Work Order
Package (WOP) contract. It defines what a WOP means, the identity and
relationship rules shared by WOP consumers, the normalized resolution
boundary, and the distinction between package content, authority, and
runtime state. It does not replace the domain owners below:

| Concern | Canonical owner | Role of this contract |
|---|---|---|
| WOP meaning, shared fields, identity, revision, immutability, normalization | this document | normative shared contract |
| Operation Alpha authorization requirements | `STD-0003` and `SPEC-0014` | domain-specific authority and admission |
| execution workflow and evidence/closeout procedure | `PROC-0001` | operational execution procedure |
| package intake and Stage 1 persistence | `ZEUS-STAGE1-RUNTIME.md` and its implementation | package boundary implementation |
| submission and admission operator boundary | `ZEUS-WOP-SUBMISSION-PROCEDURE.md` | submission procedure |
| reusable authoring shape | `TPL-0001` and the WOP authoring guide | authoring aid and template |

The secondary owners shall reference and implement this shared contract; they
shall not define competing WOP identity, revision, or resolution semantics.
Where a domain owner imposes additional safety, admission, qualification, or
explicit in-WOP approval requirements, those requirements are additive and
remain owned by that domain. The submitted WOP is the operator's work-
authority boundary for the work it contains; downstream controls validate and
constrain execution without becoming a second grant of that authority.

## Normative WOP definition

A Work Order Package is the bounded, self-contained engineering execution
contract that defines the work to be performed, its operational scope,
required bindings, execution procedure, gate and completion requirements,
verification requirements, evidence expectations, recovery behavior, and
reconciliation obligations sufficient for Zeus or a qualified execution
provider to perform the work without reconstructing operator intent.

The WOP therefore has these properties:

```text
EXECUTION_INSTRUCTION=YES
EXECUTION_SCOPE_CONTRACT=YES
SUBMITTED_WOP_WORK_AUTHORITY=YES
EXECUTION_SAFETY_RESOLUTION=REQUIRED
```

The operator-submitted WOP authorizes the bounded work it explicitly contains.
Mission, repository, baseline, provider, lifecycle, admission, and integrity
records remain required safety and identity inputs where applicable. The WOP's
lifecycle state, package presence, gate position, or readiness projection
cannot bypass those controls or independently authorize publication or
synchronization. An approval is required only when the submitted WOP declares
that approval gate.

## Canonical identity and relationships

The shared identity model is deliberately small. Each identity has one owner:

| Identity | Required | Assigned | Immutable/derived | Canonical source |
|---|---|---|---|---|
| `WOP_ID` | yes | authoring or authoritative resolution | immutable semantic identity | WOP source/authority binding |
| `PACKAGE_ID` | when materialized | packaging/admission | immutable content instance or tree identity; derived from package content | immutable manifest and package digest |
| `MISSION_ID` | when mission-bound | mission authority | immutable mission identity; not owned by the WOP | Mission Contract/authority record |
| `WORK_ITEM_ID` | when applicable | planning/registry authority | immutable external planning identity | applicable registry or roadmap authority |
| `GATE_ID` | for structured gates | WOP authoring/normalization | immutable within a WOP revision | canonical resolved WOP |
| `REVISION` | yes for submitted/revised WOPs | WOP revision transaction | immutable revision selector | WOP source and supersession record |
| `EXECUTION_ID` | after execution creation | Zeus runtime | immutable runtime transaction | execution record |
| `SESSION_ID` | after provider session creation | Zeus runtime | immutable runtime session | session record |
| `PROVIDER_ID` | after provider selection | Zeus runtime/registry | binding result, not WOP authority | selection/dispatch record |

`WOP_ID` identifies the semantic work contract. `PACKAGE_ID` identifies a
materialized content instance and must not be used as a second semantic WOP
identity. `MISSION_ID`, `EXECUTION_ID`, `SESSION_ID`, and `PROVIDER_ID` are
related runtime or authority identities and must not be generated by parsing a
human-readable projection. A WOP may be authored before final mission binding
when the applicable workflow permits it; it becomes execution-bound only when
the mission, authority, package integrity, and execution contract resolve
together.

The supported relationship is:

```text
ROADMAP (optional planning source) -> MISSION (authority) -> WOP -> EXECUTION
DIRECT MISSION (authority) -> WOP -> EXECUTION
```

Roadmap association is planning provenance, not an execution prerequisite for
an independently valid mission unless another applicable contract requires it.

## Contract layers and data classes

Every canonical WOP resolves these semantic layers, even when a legacy source
stores them in different files:

```text
IDENTITY
RELATIONSHIPS
SCOPE
AUTHORITY_REFERENCE
EXECUTION_CONTRACT
GATE_CONTRACT
EVIDENCE_CONTRACT
RECOVERY_CONTRACT
CLOSEOUT_CONTRACT
PROVENANCE / INTEGRITY
```

Data is classified by operational value:

* `REQUIRED_OPERATIONAL`: Zeus cannot safely validate, resolve, execute,
  recover, or verify the applicable operation without it; missing or invalid
  data fails closed.
* `RECONCILABLE_OPERATIONAL`: Zeus may derive it deterministically from an
  authoritative source, while recording the source and digest; reconciliation
  occurs before the fact is consumed.
* `OPTIONAL_ADVISORY`: useful for visibility or efficiency but not required for
  correct execution; absence may warn and must not independently block.
* `LEGACY`: accepted only through a compatibility/normalization path and never
  allowed to compete with a current canonical value.

No field is mandatory merely because an enterprise process commonly records
it. Administrative-only data has no execution requirement unless a separate
authority contract gives it a concrete operational purpose.

## Lifecycle, immutability, and revision

WOP lifecycle state is separate from authority and runtime execution state:

```text
AUTHORING_DRAFT -> VALIDATED_CANDIDATE -> SUBMITTED -> ADMITTED -> EXECUTION_BOUND
```

The exact repository lifecycle vocabulary remains owned by the applicable
submission and execution procedures. The semantic transitions are:

* drafts may change;
* a validated candidate is a reproducible input, but is not authority;
* a submitted package freezes its `WOP_ID`, source/package digest, revision,
  declared scope, and execution-significant inputs;
* an admitted package is bound to the admission and authority records without
  changing the WOP source;
* an execution-bound package cannot be edited in place.

A submitted WOP is never silently overwritten. A material change creates a
new revision lineage entry, preserves `supersedes`/`superseded_by` where
applicable, and retains prior execution history. A corrective may be a new
WOP or a new revision only when the applicable authority process permits it;
neither mechanism rewrites historical execution. Package content changes
normally produce a new `PACKAGE_ID`; the semantic `WOP_ID` remains stable
only when the repository's controlled revision contract explicitly permits
that relationship.

## Canonical resolution and validation contract

The logical resolution contract is shared even while implementation
convergence is staged:

```text
CANONICAL_WOP_RESOLUTION_INPUT=
  WOP source or package locator plus applicable mission/authority context
CANONICAL_WOP_RESOLUTION_OUTPUT=
  one normalized WOP projection with identities, relationships, scope,
  authority reference, execution/gate/evidence/recovery/closeout contracts,
  provenance, source digest, package digest, and lifecycle disposition
VALIDATION_ORDER=
  identity -> source/package integrity -> schema -> relationships -> locators
  -> execution/gates/evidence -> authority compatibility -> legacy normalization
AMBIGUITY_BEHAVIOR=
  fail closed; do not select a more advanced, newer, or more convenient value
```

Validation classes are `IDENTITY_VALIDATION`, `SCHEMA_VALIDATION`,
`RELATIONSHIP_VALIDATION`, `LOCATOR_VALIDATION`, `GATE_VALIDATION`,
`EXECUTION_CONTRACT_VALIDATION`, `EVIDENCE_CONTRACT_VALIDATION`,
`INTEGRITY_VALIDATION`, and `LEGACY_NORMALIZATION_VALIDATION`. Downstream
consumers should consume the normalized projection rather than independently
re-parsing source prose. WOP-M4 owns broad code convergence; WOP-M1 establishes
the contract and ordering.

## Legacy and portability policy

Historical package generations are not rewritten. Zeus classifies each input
as `CURRENT_CANONICAL`, `LEGACY_SUPPORTED`, `LEGACY_READ_ONLY`, `SUPERSEDED`,
or `INVALID`. A supported legacy package is passed through a deterministic
normalization adapter that preserves its original identity, digest, source,
and limitations. A legacy package with ambiguous identity, authority,
integrity, or execution scope is read-only or invalid rather than guessed.

The canonical user-facing submission interface is `zeus submit`. It resolves
and classifies source contract before CLI-shape routing. A valid promotable
Development source may receive identity-preserving automatic canonicalization
into the Phase-1 provenance contract: source bytes, WOP ID, Mission ID, and
source digest remain authoritative; derived template/context/output and replay
digests are recorded; an existing provenance envelope is verified. A missing
sidecar is therefore not a legacy discriminator, and `--repository` is not a
legacy discriminator. Only explicitly classified packages/admission records
use compatibility Stage 1 semantics. Ambiguous, conflicting, or digest-stale
provenance fails closed.

Submission of a WOP is authority for work explicitly contained in that WOP;
canonicalization does not create a second generic corrective, implementation,
execution, or approval grant. `approval_state` remains
`NOT_REQUIRED_UNLESS_DECLARED_IN_WOP`, while an explicit approval gate in the
WOP remains enforceable at admission or the applicable downstream boundary.

The target canonical package is transferable as one unit and will eventually
provide manifest, integrity, bootstrap, execution, gates, recovery, closeout,
and source content. WOP-M2 owns the concrete package/manifest layout. External
records are allowed only through stable, source-bound locators and remain
external authority/evidence rather than mutable package content.

## Canonical package architecture and typed extensions

The portable package contract is implemented by
`scripts.lib.wop.canonical_package` and described by
`engineering/wop/canonical-wop-package.schema.yaml`. It is a composition
layer over this shared contract and the existing immutable WOP validator; it
does not replace either legacy compatibility path. The canonical package uses
a hybrid/DAG execution graph, verification-first requirement records,
machine-attributable evidence, explicit recovery/failure/publication and
closeout boundaries, and a digest over the canonical payload.

Package authority remains external. `authority_binding` identifies the
applicable authority source but cannot make the package authoritative, and
`mission_to_mission: false` is mandatory. Dependency edges are capability,
interface, data, artifact, qualification, environment, resource,
integration, publication-baseline, or safety edges only; roadmap order,
recommendation, selection, or another mission's completion never creates
authority.

Capability-specific contracts are typed entries under `extensions`. A
non-CAGF package has no CAGF fields. The `CAGF_SOURCE_PROJECTION` extension
is the reference profile for OB-CAGF-G01 and validates source ownership,
normalized inputs, stable digests, freshness/identity rules, deterministic
generator identity, a non-authoritative derived projection, provenance,
publication policy, and byte-stability/replay qualification. The extension
does not replace the canonical owners of Mission Knowledge, Capability
Registry, EMM, PMCT, Governance, EOS, repository identity, Mission Contract,
or WOP authority.

## Future gate, recovery, and closeout minimums

WOP-M1 does not implement the WOP-M3 through WOP-M6 projections, but the
contract requires that future normalized gates provide `GATE_ID`, `OBJECTIVE`,
`ENTRY_CONDITIONS`, `EXECUTION_SCOPE`, `COMPLETION_CONDITIONS`,
`EVIDENCE_REQUIREMENTS`, `VERIFICATION_REQUIREMENTS`, `FAILURE_BEHAVIOR`, and
`NEXT_ACTION`. Future executable WOPs must expose `LAST_SAFE_STATE`,
`REPLAY_RULE`, `INTERRUPTION_REENTRY`, `FAILED_GATE_BEHAVIOR`, and
`STATE_RECONCILIATION`. Completion remains distinct from evidence,
qualification, reconciliation, and WOP closure:

```text
EXECUTION_COMPLETE -> EVIDENCE_COMPLETE -> QUALIFICATION_COMPLETE
-> RECONCILIATION_COMPLETE -> WOP_CLOSED
```

None of these states independently creates authority or publication.

## Authority

All WOP lifecycle stages consume the mission-contract-bound submission shape
and the published package resolver. The semantic WOP reference is canonical
for published Beta packages, for example
`WOP-ZDCL-01-FOUNDATION-001`. Legacy UUID WOP references remain valid for
standalone historical packages. A validator may not replace a published
semantic reference with a UUID or derive a second identity.

Approval authority and reference are resolved from the mission contract or
authoritative approval record. `approval.date` is optional when the authority
does not publish one; when present it must be ISO-8601. Missing optional dates
are omitted, never serialized as `None`.

## Validation contract

Package qualification, submission, admission, and execution share these
rules. Execution rechecks integrity, authority, repository, baseline, and
approval freshness, but does not introduce additional required fields. A WOP
that passed qualification, submission, and admission remains execution-valid
unless its package or authoritative state changed after admission.

For Development WOPs the shared contract also requires
`approval.authorized_lifecycle_state: Active`, the currently published
revisions of the governing procedure, template, and standards (`PROC-0001`,
`TPL-0001`, and `STD-0000` through `STD-0004`),
`execution_package_references.authority_node_id`,
`execution_package_references.authorization_decision_record`, and every
execution section declared by `TPL-0001`. Authoring, source validation,
submission, package projection, and `VALIDATE_WOP` consume these same fields.

The canonical sources are:

1. the mission contract;
2. the published WOP package and immutable manifest;
3. the submission and admission records;
4. the execution record and append-only evidence.

Generated and presentation projections do not own WOP identity or policy.

## Execution interface

The internal execution service accepts status, resume, suspend, and cancel
operations with an explicit execution identity. These are implementation or
read-only compatibility interfaces, not mandatory operator lifecycle steps.
The public recovery operation is `scripts/zeus resume <mission>`, which
resolves exactly one safe non-terminal execution, fails closed on ambiguity,
and reuses the existing checkpoint without creating a duplicate.

The exceptional execution-control operation is `scripts/zeus stop <mission>`.
It resolves the exact active session, proves process ownership, requests
graceful termination, escalates after a bounded timeout, preserves completed
evidence and receipts, and records an `INTERRUPTED` resumable state. It never
revokes authority, cancels a mission, or creates a replacement transaction.
Ownership or runtime-integrity failures remain fail-closed.

Queue, mission, and execution views project the same execution identity,
current gate, wait category, validation diagnostics, and next corrective
action. No view becomes an execution authority.

## Admission freshness and supersession

Admission identity includes the resolved submission ID and the current
repository baseline, in addition to mission, WOP/revision, package digest,
contract and authority bindings, principal, submitter, mode, and lifecycle
authorization. The submission ID is resolved before the request digest and
idempotency identity are calculated.

An admission records the repository baseline that formed its immutable
provenance. A baseline change does not mutate that record. For the canonical
receipt-backed lifecycle, current validity is resolved from synchronized live
`HEAD`, `origin/main`, EOS, repository identity, and verified descendant
lineage; a legitimate descendant therefore does not require rewriting or
reissuing the admission receipt. An operation that explicitly requires a
fresh equal-baseline admission must declare that stricter contract at its
boundary. The replacement admission records the prior admission, any
cancelled incompatible execution, both baselines, and the supersession
reason. Stale, superseded, rejected, or incompatible-cancelled admissions
fail closed at the execution boundary, as do non-descendant, rewritten,
identity-mismatched, forged, or ambiguous publication lineages.

## Stable operator contract

The internal admission and execution mechanisms do not change the operator
workflow. After Engineering Governance has authorized the WOP, the operator
submits it with `scripts/zeus submit <wop>`. Zeus consumes and enforces the
resolved authority. If execution is interrupted, the operator invokes only
`scripts/zeus resume <mission>`.

Zeus performs publication reconciliation, admission supersession, receipt
binding, baseline migration, runtime hydration, and recovery internally. These
operations are not additional operator-visible lifecycle steps. Publication
receipts remain immutable evidence of publication state and are never treated
as execution authority.
